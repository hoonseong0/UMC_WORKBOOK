## **1. RDB (관계형 데이터베이스)와 SQL**

![SQL이 쓰이는 관계형 데이터베이스 구조](image.png)

SQL이 쓰이는 관계형 데이터베이스 구조

### **1) RDB(Relational Database)란 무엇일까요?**

![dbms.drawio.png](dbms.drawio.png)

RDB는 데이터를 2차원의 **표** 형태로 저장하고, 여러 테이블 간의 논리적인 **관계**를 정의하여 데이터를 관리하는 데이터베이스입니다.

우리가 흔히 사용하는 **엑셀 스프레드시트**를 떠올리면 이해하기 쉽습니다.

#### **📌 테이블을 이루는 4가지 핵심 개념**

- **테이블 (Table / Entity)**: 데이터를 특정 주제별로 모아둔 독립된 표 (예: 회원 테이블, 주문 테이블)
- **열 (Column / Attribute / Field)**: 표의 세로줄. 저장할 데이터의 항목과 규격(이름, 닉네임, 생성일 등)
- **행 (Row / Record / Tuple)**: 표의 가로줄. 실제로 저장된 개별 데이터 객체 1건 (예: 1번 회원 박수현)
- **스키마 (Schema)**: 어떤 열이 들어가고, 각 열의 데이터 타입(글자, 숫자, 날짜)과 제약 조건이 무엇인지 사전에 정의해 둔 구조적 명세서

### 2) 왜 대부분의 서비스는 RDB를 기본 메인 DB로 사용할까?

스타트업부터 대기업까지, 새로운 웹/앱 서비스를 만들 때 십중팔구 메인 데이터베이스로 **MySQL**이나 **PostgreSQL** 같은 RDB를 1순위로 선택합니다.

단순히 "익숙해서"가 아니라, **서비스 운영 중 발생할 수 있는 치명적인 데이터 사고를 원천 차단해 주는 4가지 핵심 무기**가 있기 때문입니다.

#### **2-1) 데이터 중복의 원천 차단과 '단일 진실 공급원(SSOT)'**

만약 표를 하나로 합쳐서 주문 내역마다 사용자의 이름, 전화번호, 배송지 주소를 매번 통째로 적는다면 어떻게 될까요?

![NoSQL 방식](dbms.nosql.drawio.png)

NoSQL 방식

겉보기에는 한 표에 모든 데이터가 다 들어있어서 조회할 때 조인할 필요도 없고 편해 보입니다.

**🤔 그렇다면 만약 사용자가 전화번호나 배송지 주소를 바꾼 상태로 새 주문을 한다면 어떤 일이 벌어질까요?**

![dbms.plus.drawio.png](dbms.plus.drawio.png)

시스템에서는 “박수현 회원의 진짜 현재 전화번호는 둘 중 무엇인가?”하는 혼란이 발생합니다.

만약, 올바른 전화번호인 010-9012-3456으로 모두 변경 한다고 가정하면…

→ **사용자 정보를 변경하기 위해 3번의 수정이 더 필요함!**

![SQL 방식](dbms.sql.drawio.png)

SQL 방식

RDB는 이 문제를 해결하기 위해 member(회원) 테이블과 orders(주문) 테이블을 깔끔하게 분리(정규화)합니다.

#### **2-2) DB 레벨에서 강제하는 데이터 무결성 (Data Integrity)**

백엔드 개발자가 실수로 서버 코드에 버그를 만들어도, RDB 엔진 자체가 잘못된 데이터의 저장을 마지막 방어선에서 거부합니다.

- **도메인 무결성 (Type & Not Null):**
    - 나이 컬럼에 문자열 "스물다섯"이 들어오거나,
    - 필수 값인 이메일에 NULL(빈값)이 들어오면 DB가 저장을 거부합니다.
- **개체 무결성 (PK & Unique):**
    - 기본키가 겹치거나 이미 가입된 아이디/이메일로 중복 가입을 시도하면 즉시 에러를 뱉어 유일성을 보장합니다.
- **참조 무결성 (Foreign Key):**
    - 존재하지 않는 9999번 회원의 주문이 DB에 생성되는 것을 막아줍니다.
    - 부모 데이터가 없으면 자식 데이터도 생성될 수 없도록 강제하여 **고아 데이터** 발생을 차단합니다.

#### **2-3) 금융 & 이커머스의 생명선: ACID 트랜잭션**

쇼핑몰에서 결제 버튼을 누르는 순간 일어나는 3단계를 생각해 봅시다.

![acid.drawio.png](acid.drawio.png)

> **🤔**  만약 1번(출금)은 성공했는데 2번 단계에서 서버가 다운되면 어떻게 될까요?
> 
> 
> → **돈만 빠져나가고 주문은 접수되지 않는 치명적인 사고가 터집니다!**
> 

RDB는 이러한 일련의 과정을 트랜잭션이라는 하나의 작업 단위로 묶어 **ACID 원칙**을 보장합니다.

- **원자성 (Atomicity - All or Nothing)**:
    - 모든 과정이 100% 성공해야만 저장됩니다.
    - 만약, 중간에 하나라도 실패하면 시작 전 상태로 완전히 되돌립니다
- **일관성 (Consistency)**
    - 트랜잭션 실행 전후로 DB의 모든 규칙(잔액은 0원 이상 등)이 깨지지 않고 유지됩니다.
- **격리성 (Isolation)**
    - 수천 명이 동시에 결제해도 서로의 작업이 간섭받지 않도록 독립적으로 처리합니다.
- **지속성 (Durability)**
    - 결제 완료 후 서버 전원이 꺼지더라도 기록된 데이터는 영구히 보존됩니다.

#### **2-4) 단 1줄로 데이터를 엮어내는 강력한 조인 (JOIN)**

데이터를 여러 테이블로 쪼개어 보관하더라도, 화면에 보여줄 때는 언제든 원하는 형태로 합쳐서 꺼내올 수 있습니다.

- **상황**: *"안양동에 위치한 가게 중, 평점이 4.0 이상인 가게의 리뷰 목록과 작성자 닉네임을 함께 보여줘!"*
- 백엔드 코드에서 반복문을 여러 번 돌며 데이터를 하나씩 짝지을 필요 없이, **단 1줄의 SQL JOIN 쿼리**로 복잡하게 얽힌 관계형 데이터를 엔진 내부에서 고속으로 조합해 조회합니다.

### **3) RDB와 소통하는 세계 공통어 : SQL (Structured Query Language)**

RDB에 저장된 수많은 테이블과 소통하고 명령을 내리기 위해 만들어진 **표준 데이터베이스 언어**가 바로 SQL입니다.

SQL은 목적에 따라 크게 3가지 명령어로 분류됩니다.

> 
> 
> - **DDL (Data Definition Language, 데이터 정의어)**
>     - 테이블의 뼈대를 생성, 수정, 삭제하는 언어입니다.
>     - 우리가 작성할 **ERD가 바로 이 DDL 코드로 변환되어 실제 데이터베이스 뼈대**가 됩니다.
> - **DML (Data Manipulation Language, 데이터 조작어)**
>     - 만들어진 테이블 안에서 실제 데이터를 조회, 추가, 수정, 삭제하는 언어입니다.
> - **DCL / TCL (데이터 제어어 / 트랜잭션 제어어)**
>     - 사용자별 DB 접근 권한을 관리하거나, 앞서 배운 트랜잭션 작업의 저장 및 롤백을 처리하는 언어입니다.

- **MySQL, PostgreSQL, Oracle Database의 차이는 뭘까? 같은 SQL인데 그게 그거 아닌가?**
    
    혹시 이 셋의 차이에 대해서는 생각해본 적 있으신가요? 한번 간단하게 비교해 보겠습니다.
    
    ### MySQL
    
    - **장점:**
        - 오픈 소스이고 무료로 사용이 가능합니다.
        - 빠른 읽기 및 쓰기 성능을 제공하며, 특히 웹 애플리케이션에 많이 사용됩니다.
        - 업데이트 성능도 뛰어나고, **단순한 데이터 트랜잭션**에 적합합니다.
        - 또한 커뮤니티와 지원이 활발해 문제가 생겼을 때 빠르게 해결할 수 있는 참고자료들이 많다는 장점이 있습니다.
    - **단점:**
        - 복잡한 쿼리와 **복잡한 트랜잭션 처리에 취약**하다는 단점이 있습니다.
        - Nested Loop Join(바깥 테이블의 처리 범위를 하나씩 접근하면서 추출된 값으로 안쪽 테이블을 조인하는 방식)만을 지원하는데, 이는 데이터가 커졌을 때 성능 문제를 야기할 수 있습니다.
    
    ### **PostgreSQL**
    
    - **장점:**
        - PostgreSQL도 오픈 소스입니다!
        - 다양한 조인 방식을 지원하여 복잡한 데이터베이스 쿼리에서 강력한 성능을 보여줍니다.
        - **ACID** 준수 및 데이터 무결성 검증이 뛰어나고, 복잡한 트랜잭션과 **대규모 데이터베이스**에서 유리합니다. 또한 **JSON 지원** 등 최신 기술도 잘 지원합니다.
    - **단점:**
        - Update 성능이 떨어진다는 단점이 있습니다.
        - 데이터를 수정할 때 기존 데이터를 삭제하고 새로운 데이터를 삽입하는 방식으로 작동하기 때문에, 대용량 데이터 처리 시 성능 저하가 발생할 수 있습니다.
    
    ### **Oracle Database**
    
    - **장점:**
        - **고성능**, **확장성** 및 **보안**이 뛰어나며, 트랜잭션 처리가 매우 효율적입니다.
        - 또한 **대규모 엔터프라이즈 시스템**에서 많이 사용되며, 복잡한 쿼리 및 트랜잭션 처리에 매우 강합니다.
        - **분산 처리**와 **고급 기능**이 많고, Partitioning, Clustering 과 같은 고급 기능도 지원하여 매우 유연하고 강력한 시스템을 구축할 수 있습니다.
    - **단점:**
        - 가장 큰 단점은 **비용**입니다.
        - 상용 라이센스가 필요하고 가격이 비쌉니다.
        - 또한 설치와 관리가 복잡하고, 특정 기능에 대한 이해와 사용까지 오랜 시간이 걸릴 수도 있습니다.
        - 단순한 데이터베이스 관리와는 달리, 고급 기능을 잘 활용하기 위해서는 전문 지식이 필요합니다.
    
    간단하게나마 비교해 본다면 이 정도가 될 것 같습니다. 
    
    장단점을 잘 비교해 보고, 본인의 상황에 맞는 도구를 고르시면 됩니다.

## 2. NoSQL (비관계형 데이터베이스)

### **1) NoSQL(Not Only SQL)이란 무엇일까요?**

NoSQL은 Not Only SQL의 약자로 SQL을 사용하지 않는 DBMS들을 의미합니다. 

NoSQL 쪽의  데이터베이스는 key-value, document, graph 등 다양한 데이터 구조를 지원하기에 데이터가 미리 정의된 스키마를 따르지 않고 데이터 요소 간의 관계가 잘 정의되어 있지 않은 반정형 또는 비정형 데이터에 적합합니다. 

주요 NoSQL 쪽의 데이터베이스 시스템으로는 MongoDB, Redis, neo4j, DynamoDB 등이 존재합니다.

### 2) **NoSQL의 핵심 장점과 단점**

- **장점**
    - **유연한 스키마**: 기획이 바뀌어 새로운 필드가 추가되어도 DB 구조를 뜯어고칠 필요가 없습니다.
    - **초고속 성능 & 대용량 처리**: 테이블 간 조인 연산이 없기 때문에 읽기/쓰기 속도가 매우 빠릅니다.
    - **손쉬운 수평 확장 (Scale-Out)**: 데이터가 늘어나면 서버 컴퓨터를 옆으로 이어 붙여 용량을 늘리기 유리합니다.
- **단점**
    - **데이터 중복과 불일치 위험**: 회원 정보가 여러 문서에 통째로 복사되어, 정보 수정 시 데이터가 꼬일 위험(수정 이상)이 큽니다.
    - **복잡한 관계 쿼리의 한계**: 여러 데이터 간의 정교한 관계 분석이나 복잡한 집계 쿼리를 수행하기 어렵습니다.

## **3. 🤔 그렇다면 둘 중 어떤 것을 선택해야 할까요?**

정답은 "둘 중 하나만 선택할 필요가 없다"입니다!

프로젝트의 요구 사항과 서비스 성격에 맞춰 적절한 도구를 선택하는 것이 백엔드 개발자의 역량입니다.

실무에서는 주로 메인 데이터 저장을 위해 SQL(MySQL/PostgreSQL)을 중심에 두고, 빠른 읽기 성능이나 임시 데이터 캐싱이 필요할 때 NoSQL(Redis)을 조합하여 사용하는 형태를 가장 흔하게 볼 수 있습니다.

### 요구 사항

---

#### 사용자 관련 요구 사항

1. **카카오 소셜 로그인**을 구현 할 예정이다.
2. **회원 탈퇴 기능**이 필요하다.
3. **이름, 닉네임, 전화번호, 성별**이 필요하다.

#### 책 관련 요구 사항

1. **사용자가 책 여러 권을 대여**할 수 있다.
2. 책은 **하나의 카테고리**가 있다.
3. 책은 **제목, 설명에 대한 정보**가 필요하다.
4. 책 소개 페이지에 **해시태그**가 붙을 수 있고,
**책 한 권에 해시태그 여러 개**가, **해시태그 하나가 여러 책**에 붙을 수 있다.
5. 사용자가 책 설명 페이지에서 책에 **좋아요**를 누를 수 있다.
6. 책 **카테고리 별로 현재 몇 개의 책이 있는지 집계**가 필요하다.

#### 알림 관련 요구 사항

1. 알림은 **공지 관련 알림, 책 반납 시간 임박 알림, 마케팅 알림이 있을 수 있다.**
